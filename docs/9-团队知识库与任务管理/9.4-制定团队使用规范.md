## 概述

### 什么是团队使用规范？

**团队使用规范**是确保团队成员在使用 ComfyUI 时遵循的统一标准和流程。它涵盖命名规范、文件管理、版本控制、协作流程等方面。

**核心价值：**
- 📋 **统一标准**：确保团队工作一致性
- 🔄 **高效协作**：减少沟通成本和误解
- 📚 **知识传承**：便于新人快速融入
- 🛡️ **风险控制**：避免常见错误和问题

### 为什么需要制定使用规范？

| 问题场景 | 无规范 | 有规范 |
|---------|-------|-------|
| 文件管理 | 文件命名混乱，难以查找 | 统一命名，快速定位 |
| 版本控制 | 版本冲突，代码丢失 | 规范提交，历史可追溯 |
| 团队协作 | 各自为政，重复工作 | 分工明确，高效协作 |
| 知识传承 | 依赖个人，难以复制 | 文档化，可复制 |

## 命名规范详解

### 模型命名规范

#### 功能描述
统一的模型命名规范帮助团队成员快速识别模型类型、版本和用途。

#### 命名格式

```
[基础模型]_[风格/用途]_[版本]_[作者].safetensors
```

#### 参数说明

| 参数 | 说明 | 可选值 | 示例 |
|-----|------|-------|------|
| 基础模型 | 模型的基础架构 | sd15, sdxl, flux | sd15 |
| 风格/用途 | 模型的主要风格或用途 | realistic, anime, portrait | realistic |
| 版本 | 模型版本号 | v1, v2, v5, 日期 | v5 |
| 作者 | 模型作者或来源 | 作者名或来源标识 | sg |

#### 命名示例

**Checkpoint 模型：**

```
✅ 正确示例：
sd15_realistic_vision_v5_sg.safetensors
sdxl_juggernaut_xl_v9_rd.safetensors
flux_dev_20240807_official.safetensors

❌ 错误示例：
realistic_vision.safetensors          # 缺少基础模型标识
model (1).safetensors                  # 使用默认下载名称
新模型.safetensors                      # 使用中文命名
SD15_Realistic_Vision_V5.safetensors   # 大小写混用
```

**LoRA 模型：**

```
格式：lora_[类型]_[名称]_[版本].safetensors

示例：
lora_style_anime_v1.safetensors
lora_character_girl_v2.safetensors
lora_concept_mecha_v1.safetensors
```

**ControlNet 模型：**

```
格式：controlnet_[类型]_[基础模型]_[版本].safetensors

示例：
controlnet_depth_sd15_v1.safetensors
controlnet_canny_sdxl_v1.safetensors
controlnet_pose_sd15_v2.safetensors
```

#### 注意事项

1. **使用英文命名**：避免中文和特殊字符
2. **统一小写**：建议全部使用小写字母
3. **下划线分隔**：使用下划线而非空格或连字符
4. **版本号格式**：统一使用 v + 数字格式

### 工作流命名规范

#### 命名格式

```
[场景]_[用途]_v[版本].json
```

#### 命名示例

| 用途 | 命名示例 | 说明 |
|-----|---------|------|
| 文生图 | txt2img_portrait_v1.0.json | 人像文生图 |
| 图生图 | img2img_product_v1.0.json | 产品图生图 |
| ControlNet | controlnet_depth_render_v1.0.json | 深度渲染 |
| 视频 | video_animatediff_basic_v1.0.json | AnimateDiff基础 |

### 输出文件命名规范

#### 命名格式

```
[项目]_[日期]_[序号]_[描述].png
```

#### 命名示例


### 文件清理规则

#### 清理策略

| 文件类型 | 保留期限 | 清理方式 | 执行频率 |
|---------|---------|---------|---------|
| 临时输入 | 7 天 | 自动删除 | 每天 |
| 临时输出 | 30 天 | 自动删除 | 每周 |
| 项目输出 | 项目结束后 90 天 | 手动归档 | 项目结束 |
| 工作流模板 | 永久 | 版本管理 | - |

#### 清理脚本示例

```bash
#!/bin/bash
# cleanup.sh - 清理临时文件

# 清理7天前的临时输入
find input/temp -mtime +7 -type f -delete

# 清理30天前的临时输出
find output/temp -mtime +30 -type f -delete

# 清理空目录
find input -type d -empty -delete
find output -type d -empty -delete

echo "清理完成: $(date)"
```

### 分支策略

#### 分支类型

| 分支 | 用途 | 生命周期 | 合并目标 |
|-----|------|---------|---------|
| main | 稳定版本 | 永久 | - |
| develop | 开发版本 | 永久 | main |
| feature/* | 功能开发 | 临时 | develop |
| hotfix/* | 紧急修复 | 临时 | main, develop |

#### 分支命名规范

```
feature/[功能名称]    # 功能分支
feature/portrait-workflow

hotfix/[问题描述]     # 修复分支
hotfix/fix-face-detailer

release/[版本号]      # 发布分支
release/v1.2.0
```

#### 工作流程

```
1. 从 develop 创建 feature 分支
2. 开发并提交代码
3. 创建 Pull Request
4. Code Review
5. 合并到 develop
6. 测试验证
7. 合并到 main
8. 打标签发布
```

#### 详细步骤

**步骤1：创建分支**

```bash
# 从 develop 创建功能分支
git checkout develop
git pull origin develop
git checkout -b feature/portrait-workflow
```

**步骤2：开发工作流**

1. 在 ComfyUI 中开发工作流
2. 测试各项功能
3. 优化参数配置

**步骤3：测试验证**

- 功能测试：工作流可正常运行
- 兼容性测试：所需资源已准备
- 性能测试：显存占用合理

**步骤4：编写文档**

按照工作流文档模板编写说明。

**步骤5：提交 PR**

```bash
# 提交更改
git add workflows/portrait_studio_v1.0.json
git add docs/workflows/portrait_studio.md
git commit -m "feat: 添加人像摄影工作流"

# 推送分支
git push origin feature/portrait-workflow

# 在 GitHub/GitLab 创建 Pull Request
```

**步骤6：Code Review**

等待团队成员审核，根据反馈修改。

**步骤7：合并发布**

审核通过后合并到 develop，定期发布到 main。

**步骤8：通知团队**

发布更新通知。

## 常见问题 FAQ

### Q1：团队成员不遵守命名规范怎么办？

**解决方案：**

1. **培训宣贯**
   - 组织规范培训
   - 解释规范的重要性

2. **工具检查**
   - 使用自动化工具检查命名
   - Git hooks 拦截不规范提交

3. **Code Review**
   - 在审核时指出命名问题
   - 要求修改后再合并

### Q2：如何处理历史遗留的不规范文件？

**解决方案：**

1. **逐步迁移**
   - 新文件遵循新规范
   - 旧文件逐步重命名

2. **批量重命名**
   - 编写脚本批量重命名
   - 更新相关引用

3. **建立映射表**
   - 记录新旧名称对应关系
   - 便于查找和过渡

### Q3：规范太复杂，团队成员难以记住怎么办？

**解决方案：**

1. **简化规范**
   - 精简核心规范
   - 提供快速参考卡片

2. **提供模板**
   - 提供命名模板
   - 提供文档模板

3. **工具辅助**
   - 开发命名生成工具
   - 自动补全和提示

### Q4：如何平衡规范和创新？

**解决方案：**

1. **核心规范不变**
   - 命名、安全等核心规范严格执行
   - 保证团队协作效率

2. **灵活调整**
   - 允许在规范框架内创新
   - 定期评估和更新规范

3. **反馈机制**
   - 收集团队反馈
   - 持续优化规范
