## 5.5.1 把回路跑一千遍，会多出四个问题

`5.4` 的回路在「手动跑一次」的尺度上是完整的。但批量场景有四个新现实，每一个都逼出一个工程问题：

| 新现实 | 由此必须解决 |
|--------|-------------|
| 任务要跑几小时，你不能一直坐在旁边 | **调度** —— 让它自己开始 |
| GPU 一次只能干一件事，而任务排成了长队 | **并发与背压** —— 并发不是越大越好 |
| 进程会死，机器会重启 | **失败恢复** —— 断了能续、错了能重 |
| 结果有几千张，参数各不相同 | **任务台账** —— 知道跑到哪、哪张是什么参数生成的 |

这四件事与生成质量无关，它们决定了**这套东西能不能被依赖**。下面按「先有记录、再谈并发、再谈无人值守、最后谈出事怎么办」的顺序展开。

> 💡 **关于「与外部工具集成」**：ComfyUI 与外部软件协同的全部技术基础就是 `5.4` 的 API。本篇讲的是怎么把它**跑成一条稳定流水线**；把自己做成服务、供别的系统调用，是 [8.5 与内部系统对接](../8-与其他工具集成/8.5-与内部系统对接.md)。

## 5.5.2 任务台账：让每张图都能被追溯

### 为什么必须有

批量跑到第 380 张时出了张好图，你想再生成一张一样的 —— 如果没有记录，你只能靠回忆。台账要回答的是三个问题：

- **跑到哪了**（中断后从哪继续）
- **这张图是什么参数生成的**（能不能复现）
- **这批活是谁要的**（交付与对账）

### 台账放在哪：先看有几个「写手」

上一节列的三个问题，回答它们不需要什么设施 —— 台账本来就是一**张表**，问题只是这张表放在哪。

最省事的形态是**一个文件**：你的脚本直接读写它，不必额外启动任何服务进程，也不必安装任何东西（这种「单文件数据库」叫 **SQLite**；Python 自带读写它的能力）。对「一个脚本、串行跑」的批量任务，**一个文件就够了** —— 几十到几万条记录都还在它的舒适区内。

那什么时候它不够？判据只有一条：**同时有几个「写手」**。文件级的写入锁一次只容得下一个写者；一旦出现第二个要同时写的进程、或第二台机器，就得换成**独立运行、允许多写者并发的数据库服务**（**PostgreSQL** 是最常见的选择）。

| 判据 | 选择 |
|------|------|
| 一个脚本、串行写 | **SQLite** —— 一个文件，零安装、零运维 |
| 多个进程 / 多台机器同时写 | 需要独立数据库服务（PostgreSQL 等） |
| 要和别的业务库联表查询 | 同上 |

> 📌 **判据是「写者数量」，不是「数据量」。** 本材料只走到第一行 —— 后两行属于「你已经有一套在跑的数据库」的场景，其选型与部署不在本篇范围内。

### 表设计

下面就是台账的全部内容，SQLite 方言，可以直接执行：

```sql
CREATE TABLE generations (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    request_id TEXT UNIQUE NOT NULL,        -- 幂等键：同一次请求只认一个
    prompt TEXT NOT NULL,
    negative_prompt TEXT,
    seed INTEGER,
    steps INTEGER DEFAULT 20,
    cfg REAL DEFAULT 7.0,
    width INTEGER DEFAULT 512,
    height INTEGER DEFAULT 512,
    sampler TEXT DEFAULT 'euler',
    checkpoint TEXT,
    status TEXT DEFAULT 'pending',          -- pending / running / completed / failed
    prompt_id TEXT,                         -- ComfyUI 返回的任务 ID
    image_paths TEXT,                       -- 产出文件路径，JSON 数组存成文本
    created_at TEXT DEFAULT CURRENT_TIMESTAMP,
    completed_at TEXT,
    error_message TEXT
);

CREATE INDEX idx_generations_status ON generations(status);
CREATE INDEX idx_generations_created ON generations(created_at);
```

三个字段值得单独说明：

| 字段 | 为什么这么设计 |
|------|---------------|
| `request_id` | **幂等键**。脚本重启或重试时，用它判断「这条是不是已经提交过了」，避免重复出图 |
| `prompt_id` | 打通台账与 ComfyUI 历史的桥。排查时要能从台账跳到 ComfyUI 的原始记录 |
| `status` | 断点续传的依据。见下文「失败恢复」 |

> ⚠️ **参数要存全，不能只存提示词。** 同一个提示词配不同的种子、步数、采样器会出完全不同的图。想复现就必须存齐 —— 这与 [8.5 与内部系统对接](../8-与其他工具集成/8.5-与内部系统对接.md) 讲的「可复现的四个条件」是同一件事。

### 用 Python 读写它

下面是读写这张表所需的最少代码。注意它**没有引入任何第三方库** —— `sqlite3` 是 Python 自带的，不需要 `pip install`。

```python
import json
import sqlite3
import uuid
from datetime import datetime


class GenerationLedger:
    """生成任务台账：读写上面那个 SQLite 文件"""

    def __init__(self, db_path: str = "generations.db"):
        self.conn = sqlite3.connect(db_path)

    def create_task(self, prompt: str, **kw) -> str:
        """建一条 pending 记录，返回幂等键 request_id"""
        request_id = str(uuid.uuid4())
        self.conn.execute(
            "INSERT INTO generations "
            "(request_id, prompt, negative_prompt, seed, steps, cfg,"
            " width, height, status) VALUES (?, ?, ?, ?, ?, ?, ?, ?, 'pending')",
            (request_id, prompt, kw.get("negative_prompt", ""),
             kw.get("seed", -1), kw.get("steps", 20),
             kw.get("cfg", 7.0), kw.get("width", 512), kw.get("height", 512)),
        )
        self.conn.commit()
        return request_id

    def mark_running(self, request_id: str, prompt_id: str) -> None:
        self.conn.execute(
            "UPDATE generations SET status='running', prompt_id=?"
            " WHERE request_id=?", (prompt_id, request_id))
        self.conn.commit()

    def mark_done(self, request_id: str, paths: list) -> None:
        self.conn.execute(
            "UPDATE generations SET status='completed', image_paths=?,"
            " completed_at=? WHERE request_id=?",
            (json.dumps(paths), datetime.now().isoformat(), request_id))
        self.conn.commit()

    def pending(self, limit: int = 100) -> list:
        """未完成的任务 —— 断点续传的输入"""
        cur = self.conn.execute(
            "SELECT request_id, prompt FROM generations "
            "WHERE status IN ('pending','running') ORDER BY created_at LIMIT ?",
            (limit,))
        return cur.fetchall()
```

**这段代码里唯一值得盯住的是 `request_id` 的去向**：它在插入时生成，此后每一次状态迁移都用它定位记录。所以同一个任务无论被提交几次，台账里永远只有一行 —— 这就是上一节说的「幂等」落在代码上的样子。

## 5.5.3 并发与背压：并发不是越大越好

### 先看约束

ComfyUI **默认串行执行**任务（队列机制见 [5.2 队列管理](./5.2-队列管理.md)）。多个任务「同时跑」时，真正的效果是**同时占住多份显存**：

```text
单任务显存 × 并发数 > 显存总量  →  OOM
```

所以批量脚本的并发度**通常应该设在 1 到 2**。想真正提高吞吐，方向是提高单张速度（[7.3 推理加速](../7-性能优化与显存管理/7.3-推理加速.md)）或压低显存占用（[7.5 显存优化](../7-性能优化与显存管理/7.5-显存优化.md)），而不是加大并发。

> ⚠️ **常见误区：「多开几个线程就能更快」。** 如果显存已经接近上限，加大并发只会让全部任务一起变慢或一起失败。先用 [7.2 显存占用分析](../7-性能优化与显存管理/7.2-显存占用分析.md) 的方法量一下余量，再决定并发数。

### 带并发上限的批处理

```python
import concurrent.futures
import json
import random
import threading

from comfyui_client import ComfyUIClient   # 5.4 §5.4.3 的客户端

client = ComfyUIClient("127.0.0.1:8188")

results_lock = threading.Lock()
results = []


def generate_single(seed: int, prompt: str, workflow_path: str) -> dict:
    """单个生成任务"""
    with open(workflow_path, encoding="utf-8") as f:
        workflow = json.load(f)

    workflow["3"]["inputs"]["seed"] = seed
    workflow["6"]["inputs"]["text"] = prompt

    result = client.queue_prompt(workflow)
    client.wait_for_completion(result["prompt_id"])

    with results_lock:
        results.append({
            "seed": seed,
            "prompt": prompt,
            "prompt_id": result["prompt_id"],
        })
    return result


def concurrent_batch(prompts: list[str], workflow_path: str,
                     max_workers: int = 2) -> list:
    """并发生成。max_workers 通常取 1~2，理由见上文"""
    seeds = [random.randint(0, 2**32 - 1) for _ in prompts]

    with concurrent.futures.ThreadPoolExecutor(max_workers=max_workers) as executor:
        futures = [
            executor.submit(generate_single, seed, prompt, workflow_path)
            for seed, prompt in zip(seeds, prompts)
        ]
        for future in concurrent.futures.as_completed(futures):
            try:
                print(f"完成: {future.result()['prompt_id']}")
            except Exception as e:
                print(f"失败: {e}")

    return results
```

### 想真正并行，要换硬件而不是换参数

如果一张卡已经吃满，唯一有效的并行是**让多个 ComfyUI 实例各占一张卡**，再由一个调度层分发任务。这属于服务化范畴，见 [8.5 与内部系统对接](../8-与其他工具集成/8.5-与内部系统对接.md)；多卡本身的配置见 [7.4 多卡并行](../7-性能优化与显存管理/7.4-多卡并行.md)。

## 5.5.4 调度：让它自己开始

### 三种触发器

| 触发器 | 实现 | 适用 |
|--------|------|------|
| 定时 | `cron` / Windows 任务计划程序 | 每天凌晨跑一批，最简单、最可靠 |
| 定时（进程内） | APScheduler | 脚本常驻时顺手带上，可动态增删任务 |
| 事件 | Webhook / 监听目录 / 消息 | 有素材才生成，不然不跑 |

**优先用系统级的 cron 或任务计划程序。** 它不依赖你的脚本一直活着，机器重启也能恢复。

### APScheduler 示例

```python
from apscheduler.schedulers.background import BackgroundScheduler
import logging

scheduler = BackgroundScheduler()


def scheduled_batch():
    """定时批量任务"""
    prompts = load_prompts_from_file("scheduled_prompts.txt")
    for prompt in prompts:
        try:
            generate_single(random.randint(0, 2**32 - 1), prompt,
                            "workflow_api.json")
        except Exception as e:
            logging.error(f"生成失败 {prompt[:30]}: {e}")


# 每天凌晨 2:00
scheduler.add_job(scheduled_batch, 'cron', hour=2, minute=0)
scheduler.start()
```

### 定时任务的三个坑

| 坑 | 后果 | 规避 |
|----|------|------|
| **ComfyUI 没启动** | 任务全部连接失败，还白跑一轮 | 任务开头先探一次 `/queue`，不通就退出并告警 |
| **上一轮还没跑完** | 两轮同时跑，显存直接打爆 | 用文件锁或台账状态做**单实例守卫** |
| **显存被别的程序占着** | 生成变慢或 OOM | 排到业务低谷时段，或先检查显存余量（[7.2 显存占用分析](../7-性能优化与显存管理/7.2-显存占用分析.md)） |

单实例守卫的最小实现：

```python
import os

LOCK = "./batch.lock"


def run_once():
    if os.path.exists(LOCK):
        print("上一轮仍在运行，本次跳过")
        return
    try:
        open(LOCK, "w").close()
        scheduled_batch()
    finally:
        os.remove(LOCK)
```

> ⚠️ **锁文件在进程被强杀时会残留。** 更稳的做法是把「本轮是否在跑」写进台账，启动时检查状态而不是检查文件。

## 5.5.5 失败恢复：错了能重、断了能续

### 先分清哪类错误

| 类型 | 例子 | 处置 |
|------|------|------|
| **可重试** | 连接被拒、请求超时、队列满 | 等一会儿再试 |
| **不可重试** | 模型文件不存在、参数越界、模板 node ID 写错 | 重试一万次也一样，直接标记失败并告警 |
| **看情况** | 显存不足（OOM） | 降分辨率/降批量后重试，见 [7.5 显存优化](../7-性能优化与显存管理/7.5-显存优化.md) |

对第三类无脑重试是典型的错误 —— 它会用同样的参数再撞一次墙。

### 指数退避重试

```python
import time
import requests


def retry(times: int = 3, base_delay: float = 2.0):
    """只重试可重试的异常"""
    def decorator(fn):
        def wrapper(*args, **kwargs):
            last = None
            for attempt in range(times):
                try:
                    return fn(*args, **kwargs)
                except (requests.ConnectionError, requests.Timeout) as e:
                    last = e
                    delay = base_delay * (2 ** attempt)
                    print(f"第 {attempt + 1} 次失败，{delay:.0f}s 后重试: {e}")
                    time.sleep(delay)
            raise last
        return wrapper
    return decorator


@retry(times=3)
def submit(workflow: dict) -> dict:
    r = requests.post("http://127.0.0.1:8188/prompt",
                      json={"prompt": workflow}, timeout=30)
    r.raise_for_status()
    return r.json()
```

### 断点续传

台账的 `status` 字段就是断点。重启后不要从第一张重跑：

```python
import json
import random


def resume_batch(db: GenerationDB, client, workflow_path: str):
    """只跑未完成的任务"""
    with open(workflow_path, encoding="utf-8") as f:
        base = json.load(f)

    for request_id, prompt in db.pending():
        try:
            workflow = json.loads(json.dumps(base))
            workflow["6"]["inputs"]["text"] = prompt
            workflow["3"]["inputs"]["seed"] = random.randint(0, 2**32 - 1)

            result = submit(workflow)                      # 上一节那个带退避的提交
            db.mark_running(request_id, result["prompt_id"])
            client.wait_for_completion(result["prompt_id"])
            db.mark_completed(request_id, [])
        except Exception as e:
            db.mark_failed(request_id, str(e))
```

⚠️ **这里有个陷阱：** 如果任务在「已提交、未记录」之间崩溃，重启后会**重复提交**。幂等键 `request_id` 就是为了这个 —— 提交前先落库，提交后用 `prompt_id` 回填，两者对不上时以 ComfyUI 的 `/history` 为准。

### 对账

最省事的兜底是每次启动时对一次账：把台账里所有 `running` 的任务拿 `/history/{prompt_id}` 查一遍，已完成的补记、查不到的置为 `failed`。这样任何时刻中断都不会留下「永远悬着」的任务。

## 5.5.6 轻量触发器：接到你已经在用的地方

流水线跑通之后，「从哪触发」往往比「怎么跑」更影响它会不会被真正用起来。触发点越靠近使用者日常待的地方，越容易被用。

| 触发源 | 实现方式 | 说明 |
|--------|---------|------|
| 聊天工具 | Bot 监听指令 → 调 API → 回传图片 | 团队最常用的入口 |
| Webhook | 素材平台推事件 → 你的服务收 → 生成 | 素材到了才生成 |
| 表单 / 低代码 | 表单提交 → HTTP 请求节点 | 非技术同学也能用 |
| 目录监听 | 新文件落盘 → 触发生成 | 与设计工具协作时好用 |

### Discord Bot 示例

```python
import discord
from discord.ext import commands
import aiohttp

bot = commands.Bot(command_prefix='!')


@bot.command()
async def generate(ctx, *, prompt: str):
    """聊天里发一句话就出图"""
    await ctx.send(f"正在生成: {prompt[:50]}...")

    async with aiohttp.ClientSession() as session:
        async with session.post(
            "http://127.0.0.1:8188/prompt",
            json={"prompt": build_workflow(prompt)},   # 见 5.4 §5.4.6 参数化
        ) as resp:
            data = await resp.json()

    # 轮询等待（真实服务里应改用 8.5 的异步任务语义）
    path = await wait_and_fetch(data["prompt_id"])

    await ctx.send(file=discord.File(path))
```

> ⚠️ **Bot 不要直接持有 ComfyUI 的地址。** 一旦有了多个调用方（Bot、表单、业务系统），它们各自需要知道节点编号，工作流一改就全崩。正确做法是让它们统一走网关 —— 见 [8.5 与内部系统对接](../8-与其他工具集成/8.5-与内部系统对接.md) 的 `/api/generate`。

## 5.5.7 稳定性清单

上线前逐条对照。这些不是"最佳实践建议"，而是**出错后回头总结出来的原因**。

**台账与可追溯**

- [ ] 每条任务都有唯一 `request_id`，且提交前已落库
- [ ] 记录齐全的参数（种子、步数、CFG、采样器、分辨率、模型名）
- [ ] 任务失败时记录了 `error_message`
- [ ] 启动时会与 ComfyUI 对账，不留悬空任务

**资源与并发**

- [ ] 并发数经过实测（通常是 1~2），不是拍的
- [ ] 用锁或台账状态保证同时只有一轮在跑
- [ ] 生成前会检查显存余量与队列长度

**调度与恢复**

- [ ] 定时任务开头会探测 ComfyUI 是否可达
- [ ] 可重试与不可重试的错误已分开处置
- [ ] 重试有次数上限与退避，不会无限打转

**安全**

- [ ] ComfyUI 只监听内网，不直接暴露公网
- [ ] 有日志记录每次调用的来源与参数
- [ ] 输入参数有范围校验

## 常见问题

### Q1：批量跑到一半崩了，怎么接着跑？

**A：** 从台账续。

1. 启动时把所有 `running` 的任务用 `/history/{prompt_id}` 对账一次
2. 已完成的补记，查不到的置为 `failed`
3. 只重跑 `pending` 与 `failed` 的任务

**不要**从头重跑 —— 那是纯粹的算力浪费。

---

### Q2：怎么保证生成结果可复现？

**A：** 四个条件缺一不可：

- **固定种子**（`seed` 不要用 `-1`）
- **锁定模型版本**（同一个文件名不等于同一份权重，记录哈希更稳）
- **记录完整参数**（步数、CFG、采样器、分辨率）
- **记录节点包版本**（自定义节点升级会改变行为）

这正是台账里那些字段存在的理由。

---

### Q3：定时任务到点没执行？

**A：** 按这个顺序查：

1. **进程还活着吗** —— cron 的日志、任务计划程序的历史记录
2. **脚本自己能跑通吗** —— 手动执行一次
3. **ComfyUI 起了吗** —— `curl http://127.0.0.1:8188/queue`
4. **上一轮的锁还在吗** —— 残留的锁文件会让本轮直接跳过
5. **路径对不对** —— cron 的工作目录与登录 shell 不同，相对路径会失效（用绝对路径）

### Q4：并发数设多少合适？

**A：** 从 1 开始，往上加，盯住显存。

```python
# 生成过程中观察显存
# nvidia-smi --query-gpu=memory.used,memory.total --format=csv -l 1
```

只要 `单任务显存 × 并发数` 逼近显存总量，就该停手。多数家用卡上，并发 1 和并发 2 的吞吐差别很小，但 OOM 概率差别很大。

### Q5：台账用 SQLite 还是 PostgreSQL？

**A：** 判断标准是**有没有并发写**。

| 情况 | 选择 |
|------|------|
| 单一脚本、串行写 | SQLite，零运维 |
| 多个进程或机器同时写 | PostgreSQL |
| 需要在生成过程中实时查询 | PostgreSQL |

SQLite 在单写入者下完全够用；一旦有第二个进程写它就会锁库。
