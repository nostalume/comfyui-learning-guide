## 1.6.1 从一个连不上的操作开始

在空画布上放两个节点：

- `Empty Latent Image`（空白潜空间）——它只输出一样东西：`LATENT`
- `KSampler`（采样器）——它有一个名为 `model` 的输入

现在从 `Empty Latent Image` 的输出端拖一条线到 `KSampler` 的 `model` 输入。**端口不会高亮，线连不上。**

这不是操作失误，也不是软件故障。它是本文要解释的全部内容。

要理解它，先回到 [1.5 节点类型](./1.5-节点类型.md) 建立的图景：节点是一个处理单元，吃进若干输入、吐出若干输出。那么问题来了 ——

**既然节点可以两两相连，为什么不能让任意输出接到任意输入？**

---

## 1.6.2 类型：为什么端口必须声明「我搬运的是什么」

设想没有这条限制。你把一张图片接到了 `KSampler` 的 `model` 输入上。

`KSampler` 拿到它会做什么？它内部的代码是为**模型权重**写的 —— 它要在权重里做矩阵运算。拿到一张图片，它没有任何办法处理。而 ComfyUI 在执行之前，也无从知道这件事。

于是出现一个必须解决的问题：**连接的合法性，必须在拖拽那一刻就能判定**，而不能等到跑起来才发现类型不对。

一旦要求「拖拽那一刻可判定」，结论就只剩一个：**每个端口必须携带一份声明，说明自己搬运的是什么。**

这份声明就是**数据类型（data type）**。

到此为止，「数据类型」这个术语才第一次出现 —— 它不是需要先背下来的名词，而是上面这条推理的产物。**颜色也不是规定，而是类型的可视化标记**：先有类型，颜色是为了让人一眼认出来。

| 数据类型 | 颜色 | 它是什么 | **谁产出它** |
|---|---|---|---|
| `MODEL` | 薰衣草色 | 模型权重 | Load Checkpoint / Load LoRA |
| `CLIP` | 黄色 | 文本编码器 | Load Checkpoint / Load LoRA |
| `VAE` | 玫瑰色 | 图像编解码器 | Load Checkpoint / Load VAE |
| `CONDITIONING` | 橙色 | 编码后的提示词条件 | CLIP Text Encode |
| `LATENT` | 粉色 | 潜空间数据 | Empty Latent Image / KSampler |
| `IMAGE` | 蓝色 | 像素图像 | VAE Decode / Load Image |
| `MASK` | 绿色 | 遮罩 | Load Image（含遮罩时） |
| `INT` / `FLOAT` | 浅绿色 | 数字 | Primitive 类数值节点 |
| `STRING` | 浅绿色 | 文本 | Primitive 类文本节点 |

> **最后一列比颜色重要得多。** 它把「节点」与「类型」连成了一张有向图：类型由节点产出，又作为输入被别的节点消费。1.6.5 全靠这一列反推。

> **外部给定，不是推导结果：** 类型与颜色的具体对应由 ComfyUI 版本决定。某些自定义节点会使用本文未列出的类型或颜色 —— 那不矛盾，只是它们超出了核心类型的范围。

## 1.6.3 从「类型」推出的两条不对称规则

有了类型，连线规则其实只剩两条，而且两条都不是拍脑袋定的。

### 规则一：只能从输出端拖到输入端

因为数据的流动方向就是「被生产 → 被消费」的方向。画出来的线表达的是**依赖关系**：线的一端依赖另一端先算出来。

顺着这条规则，给两个方向各取一个名字会方便很多：**上游**（数据来的那一侧，即生产者）、**下游**（数据去的那一侧，即消费者）。后文都用这两个词。

### 规则二：一个输出可以接多个输入，一个输入只能接一个输出

这条不对称同样来自语义，而不是规定：

- **输出**是「一份数据被生产出来」。一份数据被多处读取不会互相干扰 —— `Load Checkpoint` 的 `MODEL` 同时接给多个采样器完全正常。
- **输入**是「一个参数取一个值」。`KSampler` 的 `model` 输入只有一个槽位，装了模型就不可能再装第二个。

### 边界：少数类型之间可以自动转换

| 原类型 | 目标类型 | 说明 |
|---|---|---|
| `IMAGE` | `MASK` | 图像转遮罩（按灰度判断） |
| `MASK` | `IMAGE` | 遮罩转图像 |

这是便利措施，不是类型系统失效。**默认假设仍然是不兼容即拒绝。**

## 1.6.4 一个常见误解：「从左到右」不是规则

你可能见过这样的说法：「ComfyUI 采用从左到右的数据流向」。

**这句话描述的是习惯，不是规则。** 把 `KSampler` 拖到 `Load Checkpoint` 的**左边**，图照样能跑对 —— 因为决定顺序的从来不是坐标，而是 1.6.3 建立的**依赖关系**。

真正的规则只有这一条：

> 一个节点只有在它的**所有上游**都算完之后，才可能开始计算。

由它可以直接推出几个现象。它们都不是可配置的选项，而是这条规则的必然结果：

- **改提示词不需要重新加载模型。** 提示词是 `CLIP Text Encode` 的参数，改动它只会让**该节点及其下游**失效重算；`Load Checkpoint` 位于它的**上游**，不受影响，模型因此不必重新载入。这条特性在 [0.3 与 WebUI 的差异对比](../0-零基础入门/0.3-与WebUI的差异对比.md) 里被列为 ComfyUI 的优势之一，现在你知道它的来源了。
- **换模型却会触发大量重算。** 因为 `Load Checkpoint` 几乎是整张图的上游，它一变，下游全部失效。
- **不可能出现环。** 如果 A 依赖 B、B 又依赖 A，这条链上没有任何一个节点能成为「第一个被计算」的节点。

## 1.6.5 反过来用：从类型推出一个最小工作流

现在把 1.6.2 的最后一列倒过来用 —— 从**终点**往回推，看一个能出图的工作流**必然**长什么样。这不是一份「推荐节点清单」，而是一次推演。

**第 1 步 · 终点是什么？**
你要一张能存下来的图片，即 `IMAGE`。消费 `IMAGE` 的节点是 `Save Image`。

**第 2 步 · `IMAGE` 从哪来？**
查表：`VAE Decode` 产出 `IMAGE`。所以链条上必须有 `VAE Decode`。

**第 3 步 · `VAE Decode` 需要什么？**
它要两样：待解码的 `LATENT`，以及一个 `VAE` 模型。于是它引出两条上游。

**第 4 步 · `LATENT` 从哪来？**
表里有两个来源：`Empty Latent Image`（产出一块空白潜空间，属于"从零画"）与 `KSampler`。此处取前者。

> 另一条路是先由 `VAE Encode` 把一张已有图片编码成 `LATENT` —— 那就是**图生图**。同一个位置换一个来源，工作流的性质就变了。见 [3.2 图生图工作流](../3-基础工作流搭建/3.2-图生图工作流.md)。

**第 5 步 · `KSampler` 需要什么？**
四样：`MODEL`、正向 `CONDITIONING`、负向 `CONDITIONING`、`LATENT`。`LATENT` 已由第 4 步供给。

**第 6 步 · `CONDITIONING` 从哪来？**
`CLIP Text Encode`。而它自己需要一个 `CLIP`。

**第 7 步 · `MODEL`、`CLIP`、`VAE` 从哪来？**
三者同源 —— `Load Checkpoint` 一次输出这三样。

推演结束。把每一步的产物列出来，**节点清单是被推出来的，不是被记住的**：

| 节点 | 它在链条上不可省的理由 |
|---|---|
| `Load Checkpoint` | `MODEL`、`CLIP`、`VAE` 三个上游的唯一源头 |
| `CLIP Text Encode` ×2 | `KSampler` 要求正向与负向两个 `CONDITIONING`，而一次编码只产出一个 |
| `Empty Latent Image` | 供给待去噪的 `LATENT`（文生图这一支） |
| `KSampler` | 唯一产出「去噪后的 `LATENT`」的节点 |
| `VAE Decode` | 把 `LATENT` 变成 `IMAGE`，链条上唯一一次类型转换 |
| `Save Image` | 终点，把 `IMAGE` 落盘 |

## 1.6.6 链条断了怎么找

既然一次执行就是沿依赖链从上游算到下游，那么「没有出图」只可能是同一个原因：

> **链条上某处断了，下游拿不到必需的输入。**

于是排查动作也只有一个方向：**从终点往回走，找第一个出错的节点。**

具体做法：找到 `Save Image`，沿着线的反方向逐个节点往回看，**第一个显示红色边框的节点就是断点**。红色边框的含义正是「我这里缺输入」—— 它就是规则一被违反时的可视信号。

以此对照几个常见现象：

| 现象 | 链条上的位置 | 动作 |
|---|---|---|
| 某节点显示红色边框 | 该节点缺必需输入 | 从它继续往上找，补上缺失的那条线 |
| 两个端口连不上 | 类型不匹配 | 对照 1.6.2 的表确认两侧类型，或改接它真正需要的输出 |
| 执行后完全没有输出 | 终点不可达 | 从 `Save Image` 往回走，找第一个红色节点 |
| 图片全黑或全白 | `VAE` 这一段断链 | 检查 `VAE Decode` 的 `vae` 输入是否接上 |
| 图片是噪点 | 链条完整，但参数越界 | 不是断链问题：检查 `steps` 是否过低、`cfg` 是否越界、模型是否正确加载 |
| 显存不足 | 与连线无关 | 资源问题，见 [7.5 显存优化](../7-性能优化与显存管理/7.5-显存优化.md) |

**把「红色边框」读成「链条上的断点」，而不是读成一个孤立的报错** —— 这是本文与列举式讲法的主要差别。

## 1.6.7 手工连线（操作清单）

> 本节是**操作清单**：写给已经知道原理、现在要动手的人。操作本身就该是清单，不承担推导。

| 操作 | 方法 |
|---|---|
| 创建连接 | 从输出端（节点右侧圆点）按住左键，拖到输入端（左侧圆点），端口高亮时松开 |
| 断开连接 | 右键点连线 → `Delete`；或把线拖到空白处松开 |
| 移动连接 | 拖住已连线的一端，改接到另一个兼容端口 |
| 断开某端口的全部连接 | `Ctrl + Alt` + 点击该端口 |
| 同时移动同一端口的整束连线 | 按住 `Shift` 拖动 |

**删除节点会连带删除它的所有连线。** 这是依赖关系的直接后果，不是软件的疏忽 —— 上游没了，下游的输入也就不成立了。

## 附录 A 编辑器操作速查

> **体裁：reference。** 键位是软件给定的**外部事实**，不由本文推出，也不在推理链上占任何位置 —— 需要时查，不需要时跳过。macOS 上 `Ctrl` 对应 `Cmd`。

| 快捷键 | 功能 |
|---|---|
| 双击画布 | 打开节点搜索面板 |
| `Ctrl + C` / `Ctrl + V` | 复制 / 粘贴节点 |
| `Ctrl + Shift + V` | 粘贴并保持外部连线 |
| `Delete` / `Backspace` | 删除选中的节点与连线 |
| `Ctrl + M` | 静音 / 取消静音（被静音的节点跳过执行，沿用上次结果） |
| `Ctrl + B` | 绕过节点（输入直接透传到输出） |
| `Alt + C` | 折叠 / 展开节点的参数区 |
| `Ctrl + G` | 把选中的节点放进分组框 |
| `P` | 固定 / 取消固定（固定后不参与自动排列） |
| `Ctrl + A` | 全选 |
| `Ctrl + D` | 快速复制 |
| `Ctrl + Z` / `Ctrl + Y` | 撤销 / 重做 |

**`Ctrl + M` 静音**在排查时格外有用：它把某个节点的输出替换为上一次执行的结果，等于**临时把上游链条摘掉**，用来判断问题是否出在这一段。这是 1.6.6「沿上游往回找」的加速手段。
