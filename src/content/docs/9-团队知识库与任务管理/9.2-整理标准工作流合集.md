# 9.2 整理标准工作流合集

> **本文承接：**
> [9.1 建立内部资源库](./9.1-建立内部资源库.md) 解决了资源放在**哪**；本文解决**放进去的是哪一份** —— 同一件事有多种做法时，团队需要一个标准。
>
> **本文引出：**
> 标准化的下一步，是让没参与制定的人也能上手 —— 见 [9.3 编写快速上手手册](./9.3-编写快速上手手册.md)。

> **相关官方文档：** [ComfyUI 官方文档](https://docs.comfy.org/) | [中文文档](https://docs.comfy.org/zh/)
> **难度等级：** 中级
> **阅读方式：** 不必通读 —— 要收模板时照着做

## 9.2.1 什么叫「一个标准」

**标准工作流**是经过验证、可复用的那**一份**节点配置：连接关系、参数、流程都定死了，谁拿来跑，结果都一样。

它和「一个能跑的工作流」是两回事。区别不在技术，在**共识**：

| 遇到的问题 | 没有标准 | 有了标准 |
|-----------|---------|---------|
| 新项目启动 | 每次从头搭，耗时以小时计 | 载入模板，几分钟完成配置 |
| 结果不一致 | 每人配置不同，出图差异大 | 同一份模板，结果可复现 |
| 经验流失 | 人一走，做法就没了 | 做法留在库里，可传承 |
| 带新人 | 只能手把手教 | 给模板自学，再对着文档提问 |

**代价也要说清楚：** 定标准意味着**放弃一部分个人偏好**，还要花时间维护它。所以只对**反复用到**的流程做标准化 —— 一次性任务不值得。

---

## 9.2.2 先分类，再决定收什么

模板一多，找东西就变成问题。**分类决定文件怎么放、怎么命名**，所以要在收第一批之前定下来。

按功能分（最常用）：

| 分类 | 做什么 | 典型用途 | 难度 |
|------|--------|---------|------|
| 文生图 | 从文字描述出图 | 创意设计、概念图 | 入门 |
| 图生图 | 基于参考图生成新图 | 风格迁移、图像修改 | 初级 |
| 高清修复 | 提升分辨率与细节 | 打印输出、成品交付 | 初级 |
| ControlNet | 精确控制构图与姿态 | 姿态控制、深度控制 | 中级 |
| 视频生成 | 生成动画或视频 | AI 动画、视频转绘 | 高级 |
| 批量处理 | 批量生成或处理 | 参数矩阵、种子遍历 | 中级 |

按用途分（便于按需求检索）：

| 用途 | 说明 | 典型模板 | 输出特点 |
|------|------|---------|---------|
| 人像 | 人物肖像 | 写实人像、艺术人像 | 细节丰富 |
| 产品 | 电商产品图 | 白底产品、场景产品 | 清晰、专业 |
| 艺术 | 创意设计 | 风格化、概念设计 | 创意性强 |
| 背景 | 场景背景 | 室内、室外、抽象 | 环境感强 |
| 角色 | 游戏 / 漫画角色 | 角色一致性、多角度 | 一致性好 |

**两层分类都要有**：功能分类决定目录结构，用途分类决定检索标签。一个模板通常同时属于两者（如「人像摄影」= 功能「文生图 + 高清修复」+ 用途「人像」）。

## 9.2.3 第一批该收哪些模板

不要一上来收几十个。**先收团队实际反复用到的** —— 多数团队的第一批是这九类：

| 模板 | 它解决什么问题 | 由哪些能力组成 | 去哪学 |
|------|--------------|--------------|--------|
| **文生图基础** | 从一段文字出一张图 | 主模型 + 提示词 + 采样 + 解码 | [3.1](../3-基础工作流搭建/3.1-文生图工作流.md) |
| **图生图** | 拿一张图改风格、改内容 | 图生图 + 重绘强度 | [3.2](../3-基础工作流搭建/3.2-图生图工作流.md) |
| **高清修复** | 小图放大后依然清晰 | 放大模型 + 二次采样 | [3.4](../3-基础工作流搭建/3.4-高清修复工作流.md) |
| **人像摄影** | 出可直接交付的人像 | 文生图 + 面部修复 + 放大 | [3.5](../3-基础工作流搭建/3.5-面部修复与细节增强.md) |
| **产品图** | 电商白底图与场景图 | 图生图 + 高清修复 | [3.2](../3-基础工作流搭建/3.2-图生图工作流.md) · [3.4](../3-基础工作流搭建/3.4-高清修复工作流.md) |
| **深度控制** | 指定空间结构、层次关系 | ControlNet + 深度预处理器 | [4.1](../4-ControlNet精准控制/4.1-ControlNet原理.md) · [4.3](../4-ControlNet精准控制/4.3-预处理器类型.md) |
| **角色一致性** | 同一个人出现在多张图里 | IP-Adapter / InstantID | [2.7](../2-模型体系与管理/2.7-IP-Adapter.md) · [4.4](../4-ControlNet精准控制/4.4-InstantID与FaceID.md) |
| **动画（AnimateDiff）** | 让静态图动起来 | 视频节点包 + 帧间一致性 | [6.3](../6-高级节点与插件生态/6.3-视频相关节点.md) |
| **视频转绘** | 把现有视频换成另一种风格 | 视频节点 + 逐帧控制 | [6.3](../6-高级节点与插件生态/6.3-视频相关节点.md) · [8.3](../8-与其他工具集成/8.3-与视频工具集成.md) |

> **本文只列「该收哪些」，不讲「每个怎么搭」。** 右列每一章都有完整的搭建步骤与参数说明；模板文件是从那一章做出来的**成品**，不是它的替代品。原因很简单：模板一旦被复制到库里就会与教程脱节 —— 你更新了做法，库里那份不会自动跟着变。所以**库里存的应当只有「已验证的成品」和「它从哪来」**。

## 9.2.4 一份模板要能被别人看懂

模板进库时，要同时交三样东西：**给人看的文档、给工具看的元数据、给审核看的测试记录**。

### 文档：每个模板配一份说明

```markdown
# 工作流名称

> **版本信息**
> - 版本：v1.0
> - 作者：[作者]
> - 更新日期：[日期]

## 用途说明

[简述应用场景与核心功能]

## 使用场景

- 场景1：[描述]

## 节点结构

[节点连接图或文字描述]

## 参数说明

| 参数 | 默认值 | 推荐范围 | 说明 |
|-----|-------|---------|------|
| ... | ... | ... | ... |

## 所需资源

### 模型
- [模型名称]：[下载位置]

### 节点包
- [节点包名称]：[安装方法]

## 使用步骤

1. [步骤1]
2. [步骤2]

## 注意事项

- [注意事项1]

## 常见问题

### Q1：[问题]
**解决方案：** [答案]
```

**关键不在于字段多，而在于「所需资源」那一节。** 别人拿到模板跑不起来，绝大多数是缺模型或缺节点包 —— 这一节写清楚了，九成的问题就不会发生。

### 元数据：跟着文件走的 JSON

如果团队有工具去读这些模板（做检索、做清单），再补一份同名 JSON：

```json
{
    "name": "工作流名称",
    "version": "1.0.0",
    "description": "工作流描述",
    "category": "txt2img",
    "author": "作者",
    "created_date": "2024-01-01",
    "updated_date": "2024-04-28",
    "required_models": [
        { "type": "checkpoint", "name": "模型名称", "download_url": "下载位置" }
    ],
    "required_nodes": [
        { "name": "节点包名称", "install_command": "安装命令" }
    ],
    "tags": ["标签1", "标签2"],
    "difficulty": "intermediate"
}
```

> 没有工具去读它的话，这一节可以先跳过 —— **不要为了规范而规范**。

## 9.2.5 收进库之前：过一遍测试清单

一份模板从「我这能跑」变成「谁都能跑」，中间隔着一次系统性验证：

```markdown
# 工作流测试清单

## 基础功能测试
- [ ] 工作流可正常加载
- [ ] 所有节点连接正确
- [ ] 参数范围合理
- [ ] 输出结果符合预期

## 兼容性测试
- [ ] 所需模型已备齐
- [ ] 所需节点包已安装
- [ ] 版本兼容性确认
- [ ] 不同分辨率下可用

## 性能测试
- [ ] 显存占用合理（记录峰值）
- [ ] 生成时间可接受
- [ ] 批量处理稳定
- [ ] 长时间运行不崩溃

## 边界测试
- [ ] 极端参数不报错
- [ ] 错误输入有合理提示
- [ ] 资源不足时行为可预期
```

**「兼容性」与「边界」两栏最容易被跳过，也最容易被抱怨。** 在一台机器上跑通的模板，换台显存小的就崩 —— 而这恰恰是模板最常见的失效方式。

## 9.2.6 版本管理

模板会被改。不改的话没人维护，改的话别人不知道改了什么。**用文件名和更新日志解决。**

### 命名

```text
工作流名称_v主版本.次版本.修订号.json

示例：
portrait_studio_v1.0.0.json    # 初始版本
portrait_studio_v1.1.0.json    # 新增功能
portrait_studio_v1.1.1.json    # 修复问题
portrait_studio_v2.0.0.json    # 重大更新
```

| 版本类型 | 含义 | 示例 |
|---------|------|------|
| 主版本 | 重大变更，**可能不兼容** | 1.0 → 2.0 |
| 次版本 | 新增功能，向后兼容 | 1.0 → 1.1 |
| 修订号 | 修 bug、小幅优化 | 1.1.0 → 1.1.1 |

**判断主版本的唯一标准：旧模板文件还能不能直接替换使用。** 要改参数才能用，就是主版本。

### 更新日志

```markdown
# 更新日志

## v1.2.0 (2024-04-28)

### 新增
- 支持多 LoRA 组合

### 优化
- 降低显存占用 20%

### 修复
- 修复 seed 不生效的问题

### 变更
- 默认采样器改为 euler_a
- 注意：此版本与 v1.1.x 配置不完全兼容
```

## 9.2.7 分享给别人

### 内部：从做完到全组可见

```text
1. 开发完成
   ↓
2. 测试验证（过 9.2.5 的清单）
   ↓
3. 编写文档（9.2.4 的三样）
   ↓
4. 提交审核
   ↓
5. 复核
   ↓
6. 合并发布
   ↓
7. 通知团队
```

第 4–5 步的审核**不是走流程**：模板的价值在于「别人能跑通」，只有第二个人真的跑通了才算验证。所以审核人应当是**没参与制作的人**。

### 对外：分享前先检查

```markdown
# 外部分享准备清单

## 文件准备
- [ ] 工作流 JSON 文件
- [ ] 使用说明文档
- [ ] 所需资源清单
- [ ] 示例效果图片

## 内容检查
- [ ] 移除敏感信息
- [ ] 检查许可证兼容性
- [ ] 确认无版权问题
- [ ] 添加使用声明

## 发布渠道
- [ ] ComfyUI 社区
- [ ] Civitai
- [ ] GitHub
- [ ] 社交媒体
```

> **「内容检查」这四条是给自己的保护。** 工作流文件里可能带着本机路径、内部模型名、客户项目名；用的模型与 LoRA 也可能有各自的许可限制。

## 9.2.8 常见问题

### 载入后节点是红色的

缺自定义节点包。按 [6.5 自定义节点安装](../6-高级节点与插件生态/6.5-自定义节点安装.md) 里的方法处理（ComfyUI Manager 的 `Install Missing Nodes` 是最快的一条）。

### 怎么快速找到合适的工作流

三步：先按**用途**筛（人像 / 产品 / 艺术…），再看**示例效果**判断是否符合需求，最后看**难度**是否超出你的把握。这也是 9.2.2 要同时维护两层分类的原因。

### 别人的模板，参数能不能直接改

能，但要守两条：**一次只改一个参数**，**改动幅度小（±10% 量级）**。改完记录前后差异 —— 否则出了问题无法回退，也无法知道是哪一步造成的。

### 想自己做一份模板

顺序是：先用现成模板跑通 → 逐步加节点、每加一个就测一次 → 参数调到位 → 按 9.2.4 补文档、按 9.2.5 过清单。**别一上手就从空白画布搭** —— 你会在同时调试太多变量。

### 版本升级后不兼容怎么办

先别删旧版本（文件名带版本号就是为了这个）。对照更新日志看改了什么，在新版本里把旧配置**逐项**复现，确认效果后再全面切换。

## 时效性说明

| 项目 | 说明 | 检查频率 |
|-----|------|---------|
| 模型版本 | 新模型往往需要调整模板 | 每月 |
| 节点更新 | 节点参数可能变化，会让旧模板失效 | 每周 |
| 最佳实践 | 持续演进 | 持续 |
| 兼容性 | 需定期重新验证 | 每月 |
