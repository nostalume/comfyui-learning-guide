# 7.5 显存优化

> **相关官方文档：** [ComfyUI 官方文档](https://docs.comfy.org/) | [中文文档](https://docs.comfy.org/zh/)

> **本文承接：**
> [7.2 显存占用分析](7.2-显存占用分析.md) 已经把显存拆成了一本账：权重按「参数量 × 精度位数」占，激活值按分辨率的平方涨，缓存与碎片随时间累积。本文接着这本账做处置 —— 哪一项能直接砍掉、哪一项只能搬走、搬走要付什么代价。
>
> **本文引出：**
> 显存优化解决的是「在既有硬件上把模型塞进去」。它的两条邻路是 [7.3 推理加速](7.3-推理加速.md)（同样的计算算得更快）与 [7.4 多卡并行](7.4-多卡并行.md)（换更多硬件）。三条路都用尽之后，问题就从「怎么跑」变成「跑在哪个系统里」，那从第 8 章 [8.1 与 AI 绘画平台集成](../8-与其他工具集成/8.1-与AI绘画平台集成.md) 开始。

## 概述

### 显存里的四笔账

优化显存不是记住一堆参数，而是先看清显存被什么占着。ComfyUI 运行时的显存支出只有四笔：

| # | 占哪一笔 | 由什么决定 | 典型量级 |
|---|---|---|---|
| 1 | **模型权重** | 参数量 × 每个参数的字节数 | SD 1.5（FP16）约 1.8GB；SDXL 约 5GB |
| 2 | **激活值** | 分辨率的**平方** × 批量（线性） | 1024×1024 时可达数 GB，是峰值的主要来源 |
| 3 | **缓存与碎片** | 已加载模型是否释放、运行了多久 | 换过几次模型后累积 |
| 4 | **基础开销** | CUDA 上下文、驱动、界面 | 约 500MB–1GB |

这四笔账的性质完全不同，于是处置手段也只有三条：

| 出路 | 打的是哪一笔 | 手段 | 本文哪一节 |
|---|---|---|---|
| **降精度** | 第 1 笔的「每参数字节数」 | FP16 / BF16 / FP8 | [精度量化](#精度量化直接改小每个参数的位数) |
| **减少同时驻留** | 第 1 笔的「同时在场数量」 | 分块加载、权重卸载 | [分块加载](#分块加载把权重留在内存按需搬进显存) |
| **压峰值** | 第 2 笔 | 分辨率、批量、少挂 ControlNet | [工作流侧的五个动作](#工作流侧的五个动作) |

第 3、4 笔压不掉，只能缓解：给 `--reserve-vram` 留一块缓冲，或者重启 ComfyUI 清掉碎片。

**先确认真的需要优化。** 显存充足时上面每一条都会让速度变慢、或让画质略降。**能跑满速就别改** —— 只有在出现 OOM、或者想跑到原本跑不动的模型/分辨率时，才往下看。

## 四种显存模式：默认自动，参数是强制覆盖

先纠正一个常见误解：**ComfyUI 默认就是自动的**。它启动时会读你的可用显存，不够时自行启用低显存策略。所以下面四个参数不是「必须选一个」的选项，而是**在你不同意自动判断时用来强制覆盖它**。

| 模式 | 启动参数 | 显存占用 | 速度 | 什么时候用它 |
|-----|---------|---------|------|------|
| **高显存** | `--highvram` | 100% | 最快 | 显存远大于模型，想消掉所有搬运 |
| **正常（默认）** | 不加参数 | ~70% | 较快 | 自动判断切到了 lowvram，但你其实够用 |
| **低显存** | `--lowvram` | ~40% | 较慢 | 自动判断没切、但实际已经 OOM |
| **无显存** | `--novram` | ~20% | 最慢 | 显存极小，只求跑通 |

> 如果只是想让启动后自动打开浏览器，那是另一个参数 `--auto-launch`，**它与显存模式无关**。

### 怎么选

按显存容量对照下表；**判断顺序仍是先不加参数跑一次**（见下）。

| 显存 | 选择 |
|---|---|
| 24GB+ | 不动（默认即可） |
| 16GB | 不加参数（默认模式） |
| 12GB | 不加参数（默认模式） |
| 8GB | 不加参数（默认模式），跑 SDXL 时 `--lowvram` |
| 6GB | `--lowvram` |
| 4GB | `--lowvram` 或 `--novram` |

**判断顺序：先不加参数跑一次**，看启动日志里 ComfyUI 自己选了哪个模式；只有在它选错、或仍然 OOM 时才手工覆盖。

## 分块加载：把权重留在内存，按需搬进显存

`--lowvram` / `--novram` 背后的机制是**分块加载**：模型权重常驻系统内存（RAM），计算推进到哪一块，就把哪一块搬进显存，算完立刻释放，下一块再搬。

```text
系统内存 (RAM)                    GPU 显存
  模型权重全部在这里
        │
        ├── 块 1 ────搬入───→  计算 → 释放
        ├── 块 2 ────搬入───→  计算 → 释放
        ├── 块 3 ────搬入───→  计算 → 释放
        └── …
```

这解释了低显存模式为什么慢：**慢在搬运，不在计算**。每一块都要过一次 PCIe，块越多、搬得越勤，速度损失越大。也解释了为什么低显存模式不改变画质 —— 权重数值一个没变，只是换了个地方待着。

代价对照（相对高显存模式）：

| 模式 | 显存节省 | 速度损失 | 本质 |
|---|---|---|---|
| *(默认模式)* | — | 基准 | 少数层搬来搬去 |
| `--lowvram` | ~60% | −30~50% | 大部分层搬来搬去 |
| `--novram` | ~80% | −50~70% | 几乎所有层都在搬 |

## 精度量化：直接改小每个参数的位数

如果显存的第一笔账是「参数量 × 每参数字节数」，那么**不换模型、也不搬来搬去，直接把字节数减半**，是最省事的一刀。

| 精度 | 位数 | 显存占用 | 速度 | 画质 | 硬件要求 |
|-----|------|---------|------|------|---------|
| FP32 | 32 位 | 100% | 基准 | 最高 | 所有 GPU |
| FP16 | 16 位 | 50% | +30% | 几乎无损 | 所有 NVIDIA GPU |
| BF16 | 16 位 | 50% | +30% | 更稳定 | RTX 30/40+ |
| FP8 | 8 位 | 25% | +20% | 轻微损失 | RTX 40+ |
| INT8 | 8 位 | 25% | +30% | 有可见损失 | 需要额外量化 |

### FP16：默认就走这条路

ComfyUI **默认已启用 FP16**，多数情况下不需要手动加参数；只有在显式关掉过、或想确认时才对症下药。

```bash
python main.py --fp16-unet --fp16-vae
```

| 参数 | 作用 | 建议 |
|-----|------|-------|
| `--fp16-unet` | U-Net 用 FP16 | 默认已开 |
| `--fp16-vae` | VAE 用 FP16 | 默认已开 |
| `--fp16-text-enc` | 文本编码器用 FP16 | 可选 |

副作用：少数模型在 FP16 下会出 NaN（画面纯色或黑图）。遇到就换 BF16。

### BF16：数值范围更大，更不容易炸

BF16 和 FP16 一样占 2 字节，但把位数分配给了指数位，因此**动态范围与 FP32 相同**，溢出风险低得多。

| GPU 系列 | BF16 支持 |
|---------|---------|
| RTX 40 / 30 系列 | ✅ 完全支持 |
| A100 / H100 | ✅ 完全支持 |
| RTX 20 系列及更早 | ❌ 不支持 |

```bash
python main.py --bf16-unet
```

| 特性 | FP16 | BF16 |
|------|------|------|
| 数值范围 | 较小 | 较大（同 FP32） |
| 有效精度 | 较高 | 较低 |
| NaN 风险 | 较高 | 较低 |
| 硬件要求 | 所有 GPU | RTX 30/40+ |

**结论：RTX 30/40 及以上一律优先 BF16**，只有在不支持的旧卡上才退回 FP16。

### FP8：再砍一半

FP8 把每个参数压到 1 字节，显存只有 FP16 的一半。

| GPU | FP8 支持 |
|-----|---------|
| RTX 40 系列 | ✅ 支持 |
| H100 | ✅ 支持 |
| RTX 30 / 20 系列 | ❌ 不支持 |

```bash
# 只量化 U-Net
python main.py --fp8_e4m3fn-unet

# 连文本编码器一起量化
python main.py --fp8_e4m3fn-unet --fp8_e4m3fn-text-enc
```

| 参数 | 作用 | 说明 |
|-----|------|------|
| `--fp8_e4m3fn-unet` | U-Net 用 FP8 E4M3FN | 首选，精度保留更好 |
| `--fp8_e5m2-unet` | U-Net 用 FP8 E5M2FN | 范围更大、精度更低 |
| `--fp8_e4m3fn-text-enc` | 文本编码器用 FP8 | 提示词遵循度要求高时慎用 |

效果：显存约为 FP16 的一半，速度再快约 20%，画质有轻微、通常不可察觉的损失。**FP8 是「显存实在不够」时的手术刀，不是默认配置。**

### 按显卡选精度

| GPU | 推荐精度 |
|-----|---------|
| RTX 40 系列 | BF16；显存告急时 FP8 |
| RTX 30 系列 | BF16 |
| RTX 20 系列 | FP16 |
| GTX 系列 | FP16 |

## 其余开关

上面三条出路之外，还有几个只影响单点的小开关：

| 参数 | 作用 | 代价 |
|-----|------|------|
| `--reserve-vram <GB>` | 预留一块显存不用，避免被别的程序挤到 OOM | 可用显存变少 |
| `--fp16-vae` / `--bf16-vae` | VAE 也用半精度 | 与 U-Net 一致即可 |
| `--cpu-vae` | 把 VAE 解码放到 CPU | 省 100–200MB，解码慢 2–3 倍 |
| *(默认启用)* | xFormers：装了即自动生效，不需要参数 | 见 [7.3 推理加速](7.3-推理加速.md) |
| `--use-pytorch-cross-attention` | 同上，换成 PyTorch 内置 SDPA | 见 [7.3 推理加速](7.3-推理加速.md) |

`--reserve-vram` 是唯一「拿可用显存换稳定性」的参数，取值建议：

| 值 | 含义 | 场景 |
|---|------|------|
| 0.5 | 留 0.5GB | 显存极度紧张，可能仍不稳定 |
| 1.0 | 留 1GB | **推荐起点** |
| 2.0 | 留 2GB | 系统里还有别的程序在吃显存 |

**注意：** ComfyUI **没有** `--use-xformers` 这个参数（那是 WebUI 的）—— xFormers 只要装在环境里，启动时就**自动启用**。同一时刻只会用一种注意力实现：想改用 PyTorch 的 SDPA 就显式加 `--use-pytorch-cross-attention`，想彻底关掉 xFormers 用 `--disable-xformers`。

## 按显存给配置

把前面所有手段合起来，按显存档位给一套可直接抄的配置：

| 显存 | 模式 | 精度 | 显存相关开关 | 能跑到哪 |
|-----|------|------|------|-----------|
| 4GB | `--lowvram` | FP16 | `--cpu-vae --reserve-vram 0.5` | SD 1.5 @ 512×512 |
| 6GB | `--lowvram` | FP16 | — | SD 1.5 全功能；SDXL @ 1024 勉强 |
| 8GB | *(默认)* | FP16 | — | SDXL @ 1024；SDXL + 单个 ControlNet |
| 10GB | *(默认)* | FP16 | `--bf16-vae` | SDXL + 多个 ControlNet |
| 12GB | 默认 | BF16 | `--bf16-vae` | SDXL 全功能 |
| 16GB | 默认 | BF16 | — | SDXL 高分辨率；Flux 低显存 |
| 24GB+ | 默认 | BF16 | — | 所有模型，含 Flux 标准模式 |

四套常见硬件对应的完整命令：

```bash
# 4GB：能跑通 SD 1.5 就算成功
python main.py --lowvram --fp16-unet --fp16-vae --cpu-vae --reserve-vram 0.5

# 6GB：SD 1.5 全功能，SDXL 勉强能出图
python main.py --lowvram --fp16-unet --fp16-vae

# 8GB：SDXL 的主力档位
python main.py --fp16-unet --fp16-vae

# 12GB 及以上：优先稳定与速度，不再为显存牺牲
python main.py --bf16-unet --bf16-vae
```

加速相关只需在需要时显式指定注意力实现（`--use-pytorch-cross-attention` / `--use-flash-attention`）；xFormers 装了就是默认。显卡对照表见 [7.3 推理加速](7.3-推理加速.md)，与上表不冲突。

## 工作流侧的五个动作

参数是启动时的一次性决定，工作流里的设置才是每次生成都在生效的那部分。按对峰值（激活值）的影响从大到小：

### 一、先降分辨率

分辨率对激活值的影响是**平方级**的 —— 边长翻倍，占用约 4 倍：

| 分辨率 | 相对显存 | 像素数 |
|-------|---------|-------|
| 512×512 | 1× | 262,144 |
| 768×768 | 2.25× | 589,824 |
| 1024×1024 | 4× | 1,048,576 |
| 1536×1536 | 9× | 2,359,296 |

所以最省显存的出图方式是**先低分辨率、再放大**：512×512 生成底图，再用高清修复（见 [3.4 高清修复工作流](../3-基础工作流搭建/3.4-高清修复工作流.md)）放到 1024×1024，比直接生成 1024×1024 峰值低得多。

### 二、把批量降到 1

`batch_size` 对显存是线性叠加的，在 `Empty Latent Image` 节点里设。批量本身就是一种「用显存换吞吐」的取舍，完整讨论见 [5.1 批量生成](../5-自动化与批量生成/5.1-批量生成.md)。

### 三、少挂 ControlNet

每个 ControlNet 额外吃 **700MB–1.5GB**。显存紧张时只挂真正必要的那一个，并优先选轻量预处理器。

### 四、换更轻的模型

| 模型 | 显存需求 | 质量 | 速度 |
|-----|---------|------|------|
| SD 1.5 / SD 2.1 | ~4GB | 好 | 快 |
| SDXL Turbo | ~6GB | 好 | 很快 |
| SDXL | ~8GB | 很好 | 中 |
| Flux.1 Schnell | ~12GB | 极好 | 慢 |

### 五、把 VAE 放到 CPU

显存只剩最后一两百兆时，`--cpu-vae` 往往是「跑通」与「OOM」的分界。

在 RTX 3060 12GB 上实测的量级参考：

| 配置 | SD 1.5 @512 | SDXL @1024 |
|-----|-----------------|-----------------|
| 默认 | ~5GB | ~12GB |
| + FP16 | ~3GB | ~7GB |
| + `--lowvram` | ~2GB | ~4GB |

| 配置 | SD 1.5 @512 | SDXL @1024 |

| + BF16 | 2.0s | 4.0s |
| + torch.compile | 1.8s | 3.6s |

**注意方向：显存优化与速度在多数手段上是相互牺牲的**；上表里「+ BF16」「+ torch.compile」之所以又快又省，是因为它们改的是精度与编译，而不是搬运。

## 出问题时按这个顺序排查

出现 `CUDA out of memory` 时，不要一次全开 —— **按下列顺序逐个加，加一个跑一次**，才能知道是哪一项救了你：

| 顺序 | 动作 | 效果 | 难度 |
|-----|------|------|------|
| 1 | 降低分辨率 | ⭐⭐⭐⭐⭐ | 简单 |
| 2 | 启用低显存模式 `--lowvram` | ⭐⭐⭐⭐⭐ | 简单 |
| 3 | 批量大小降到 1 | ⭐⭐⭐⭐ | 简单 |
| 4 | 启用 FP16 / BF16 | ⭐⭐⭐⭐ | 简单 |
| 5 | 启用 xFormers 或 SDPA | ⭐⭐⭐ | 中等 |
| 6 | 减少 ControlNet 数量 | ⭐⭐⭐ | 简单 |
| 7 | 使用 CPU VAE | ⭐⭐ | 简单 |

到这七步仍然 OOM，就说明这个模型/分辨率在你的卡上确实没有余量了；下一步是 [7.4 多卡并行](7.4-多卡并行.md)，或者换更轻的模型。

**先看清是谁占的，再动手** —— 具体是权重太大还是激活值太高，用 [7.2 显存占用分析](7.2-显存占用分析.md) 的监控方法量一次就知道了，这比盲试参数快得多。

## 常见问题 FAQ

### Q1: 优化之后画质会下降吗？

- **FP16 / BF16**：几乎无影响，肉眼不可分辨
- **FP8**：轻微影响，多数场景不可察觉；提示词细节多时可能丢失
- **分块加载（低显存模式）**：**完全无影响**，它只改变权重待在哪里，不改变数值
- **降分辨率、减批量**：改的是构图与细节量，不是「画质损失」，而是换了个画法

### Q2: 怎么确认优化真的生效了？

三处对照：启动日志里 ComfyUI 报告的显存模式与精度；`nvidia-smi` 看到的峰值占用（方法见 [7.2 显存占用分析](7.2-显存占用分析.md)）；同一工作流的单张耗时。

### Q3: 多个优化参数可以组合吗？

多数可以，但有两组互斥：

```bash
# 推荐组合：省显存三件套
python main.py --lowvram --fp16-unet

# 不行：两者互斥，后者会被忽略
python main.py --use-pytorch-cross-attention
```

`--fp16-unet` 与 `--bf16-unet` 也只能留一个 —— 同时给没有意义。

### Q4: 出现 NaN（黑图 / 纯色图）怎么办？

按可能性依次排查：换 BF16 替代 FP16 → 降低 CFG Scale → 确认模型文件本身没损坏 → 更新 PyTorch。

### Q5: 低显存模式下敢跑 SDXL 吗？

可以。8GB 显存跑 SDXL @1024×1024 的推荐组合：

```bash
python main.py --lowvram --fp16-unet --fp16-vae --reserve-vram 0.5
```

配套工作流设置：分辨率 1024×1024、`batch_size` 1、步数 20、采样器 `euler_a`。

### Q6: 换了模型之后越来越卡，是显存泄漏吗？

多数不是泄漏，而是**模型缓存**：ComfyUI 默认保留已加载的模型以便下次直接用，换过几个大模型后显存就不再回收。处理办法是重启 ComfyUI；需要在代码里主动释放时：

```python
import comfy.model_management as mm

mm.unload_all_models()
```
